# Requirements Document

## Introduction

`phase-4-agentic` delivers Phase 4 of the MatchLayer roadmap: the Agentic AI system. Phase 3 shipped three one-shot LLM features (resume coach, bullet rewriting, interview question generation) behind a provider-neutral `LLM_Client`, with PII redaction, cost controls, invocation logging, and universal fallbacks. Phase 4 restructures the AI layer into composable agents orchestrated with **LangGraph**: each agent is a graph node, a typed Pydantic state schema flows between nodes, and graph state persists via LangGraph's Postgres-backed checkpointer. The result is a multi-step analysis pipeline that produces everything Phase 3 returned plus structured per-agent traces.

Five nodes make up the graph. The **Resume Analysis Agent** (LLM) extracts a structured candidate profile — sections, skills, experiences, gaps — from resume text. The **ATS Agent** (deterministic, no LLM) wraps the Phase 2 composite scorer and tags its output with a confidence level. The **Skill Gap Agent** (deterministic, no LLM) identifies missing and weak skills relative to the job description, prioritized by importance, building on the Phase 2 skill extraction and the persisted Match_Result. The **Resume Improvement Agent** (LLM) generates rewrites and additions, calling Phase 3's coach prompt internally through the existing prompt registry. The **Synthesizer** (non-LLM) combines all outputs into the final response. At most two nodes make LLM calls per run — a deliberate cap that keeps cost and latency bounded and honors the phase doc's "LLMs only where reasoning is genuinely needed" rule.

Execution is asynchronous, because a multi-agent run takes tens of seconds: `POST /api/v1/matches/{id}/analyze` returns `202 Accepted` with a job id, and the client polls `GET /api/v1/jobs/{id}` for status. **SQS is introduced in this phase** (originally slated for Phase 6) because async is now a real product requirement: the API enqueues jobs, and a dedicated worker process drains the queue and runs the graph. Locally SQS is emulated (LocalStack in docker-compose); in the deployed environment real AWS SQS is used, which fits the free tier (1M requests/month) at expected volume — an explicit acknowledgment against the $20/month Phases 1–5 cost ceiling.

Phase 3's LLM plumbing is **reused, never duplicated**. Every agent LLM call flows through the existing `LLM_Client`; the `PII_Redactor` transforms text before any provider transmission; the Daily_Quota and Spend_Circuit_Breaker govern agent calls exactly as they govern Phase 3 features — with quota accounting extended to recognize that one agent run may consume up to two quota units; every call lands in the `llm_invocation_logs` table with prompt version, model, input hash, latency, and cost; prompts are versioned files resolved through the Phase 3 registry; and every LLM failure degrades to a schema-conformant non-LLM output, never a 500. Per-agent caching keyed by `(agent, input_hash)` reduces repeat spend.

Observability is a first-class deliverable: OpenTelemetry tracing enters the stack here (per `tech.md`, "introduced in Phase 4 when async workflows appear"), with every agent invocation a span. Each agent run is persisted in an `agent_runs` table for debugging and replay, alongside an `agent_jobs` table tracking job lifecycle. Agent traces are classified Internal per `security.md`, but resume text carried inside them is Restricted — persisted agent state therefore carries redacted or derived content and never raw PII, and trace access is scoped to the owning user. The reproducibility bar: trace data alone is sufficient to reproduce any past run from its inputs.

The frontend adds a polling-based progress UI ("Analyzing… ATS scoring… Generating improvements…"), per-step status display, and a "Show reasoning" toggle revealing per-agent outputs. Streaming step results as they complete is an explicit nice-to-have, not a requirement.

One correction to the phase doc: it names the architecture doc `docs/adr/0004-agent-architecture.md`, but ADR 0004 already exists (pgvector). Per the ADR conventions in `adrs.md` (sequential numbering, immutable once accepted), the agent architecture ADR is **`docs/adr/0008-agent-architecture.md`**.

Per ADR 0001 (phase gating), Phase 4 builds nothing for Phase 5+: no DeepEval suites, no evaluation dashboard (Phase 5 consumes the traces and invocation logs this phase produces), no multi-resume batch processing, no tool-use beyond what the graph needs, and no multi-turn conversational agents. This document does not restate the cross-cutting baselines from `security.md`, `conventions.md`, `structure.md`, or `tech.md`; individual requirements reference the clauses they depend on.

Scope boundaries:

- **In scope:** a LangGraph-orchestrated agent workflow with a typed Pydantic state schema and Postgres-backed checkpointing; five agents (Resume_Analysis_Agent, ATS_Agent, Skill_Gap_Agent, Improvement_Agent, Synthesizer) each with a single responsibility; parallel graph branches where agents are independent; per-node graceful degradation so one failing agent never fails the whole graph; async execution via `POST /api/v1/matches/{id}/analyze` (202 + job id) and `GET /api/v1/jobs/{id}` polling; SQS (LocalStack locally, AWS SQS deployed) with a worker process and worker Dockerfile; `agent_jobs` and `agent_runs` tables with Alembic migrations; reuse of the Phase 3 LLM_Client, PII_Redactor, Daily_Quota (extended for multi-call runs), Spend_Circuit_Breaker, LLM_Invocation_Log, prompt version registry, and fallback discipline; per-agent result caching keyed by agent and input hash; OpenTelemetry tracing with a span per agent invocation; run reproducibility from persisted trace data; end-to-end typical runs under 30 seconds; frontend polling progress UI with per-step statuses and a "Show reasoning" toggle; `/healthz` reporting the agent subsystem; OpenAPI→TS/Zod codegen coverage of the new endpoints; configuration, `.env.example`, README runbook, `docs/costs.md` update, and `docs/adr/0008-agent-architecture.md`.
- **Out of scope:** the evaluation framework, DeepEval suites, and evaluation dashboard (Phase 5 — Phase 4 only produces the traces and logs those consume); multi-resume comparison or batch processing; tool-use beyond graph needs (no web search, no code execution); multi-turn conversational agents; streaming of agent step results over SSE/WebSocket (explicitly a nice-to-have that MAY ship but is not required); modifying the Phase 1/2 scoring pipeline or the Phase 3 feature endpoints (they continue to work unchanged); ECS/Fargate worker deployment and the broader AWS migration (Phase 6 — Phase 4's worker runs on the existing Fly.io/docker footprint); recruiter-side workflows (Phase 7); payment or metered billing (Phase 7).

## Glossary

- **API_App** — The FastAPI application at `apps/api/` exposing the Python package `matchlayer_api`, as established in Phase 1.
- **Web_App** — The Next.js frontend at `apps/web/` established in Phase 1, with the `(app)` authenticated route group that is never indexed per `seo.md`.
- **User_Account** — The authenticated principal from `phase-1-auth` that owns every Resume, Match_Result, Agent_Job, and Agent_Run.
- **Match_Result** — A row in the `match_results` table from Phase 1/2, owned by a User_Account, holding the score, breakdown, matched/missing skills, and suggestions for one resume + job-description pair.
- **Resume** — A row in the `resumes` table from Phase 1, owned by a User_Account, holding `extracted_text` (Restricted PII).
- **Job_Description** — The plain-text job description stored with a Match_Result, classified Restricted per `security.md`.
- **LLM_Client** — The Phase 3 provider abstraction in `apps/api/src/matchlayer_api/ml/llm/` through which all LLM_Provider calls flow. Phase 4 reuses it unchanged for all agent LLM calls.
- **PII_Redactor** — The Phase 3 component that regex-redacts emails, phone numbers, and obvious full names into indexed typed placeholders before any text is sent to the LLM_Provider. Phase 4 reuses it unchanged.
- **Daily_Quota** — The Phase 3 per-User_Account limit on LLM_Provider-calling requests per UTC day (default 25, Redis-accounted). Phase 4 extends its accounting to multi-call agent runs.
- **Spend_Circuit_Breaker** — The Phase 3 global monthly LLM spend limit (default $10) that disables LLM features app-wide when crossed. Phase 4 agent LLM calls count against it and respect its open state.
- **LLM_Invocation_Log** — The Phase 3 persisted record of a single LLM_Provider call (prompt version, model, input hash, output, latency, token usage, cost). Every agent LLM call produces one.
- **Prompt_Template** — A versioned prompt file in `apps/api/src/matchlayer_api/ml/prompts/` resolved through the Phase 3 active-version registry.
- **Agent** — A single node in the Agent_Graph with exactly one responsibility, implemented as a function over Agent_State. An Agent is either an LLM_Agent (calls the LLM_Client) or a Deterministic_Agent (no LLM call).
- **LLM_Agent** — An Agent whose output is produced via an LLM_Client call: the Resume_Analysis_Agent and the Improvement_Agent. These are the only two LLM_Agents in the graph.
- **Deterministic_Agent** — An Agent that makes no LLM_Provider call: the ATS_Agent, the Skill_Gap_Agent, and the Synthesizer.
- **Agent_Graph** — The LangGraph-compiled workflow in `apps/api/src/matchlayer_api/ml/agents/graph.py` wiring the five Agents with edges encoding execution order and parallel branches.
- **Agent_State** — The typed Pydantic model in `apps/api/src/matchlayer_api/ml/agents/state.py` passed between Agent_Graph nodes, carrying identifiers, derived/structured content, per-agent outputs, and per-agent status flags. Never carries raw unredacted Resume text.
- **Checkpointer** — LangGraph's built-in Postgres-backed persistence mechanism storing Agent_Graph state snapshots so an in-flight or completed graph execution can be inspected and resumed.
- **Resume_Analysis_Agent** — The LLM_Agent that extracts a Candidate_Profile (sections, skills, experiences, gaps) from redacted Resume text.
- **Candidate_Profile** — The schema-validated structured output of the Resume_Analysis_Agent.
- **ATS_Agent** — The Deterministic_Agent that runs the Phase 2 composite scorer (`Semantic_Match_Scorer`) and tags the result with a Confidence_Level.
- **Confidence_Level** — The tag the ATS_Agent attaches to its score: exactly one of `high`, `medium`, or `low`, derived by a documented deterministic rule.
- **Skill_Gap_Agent** — The Deterministic_Agent that produces a Skill_Gap_Report from the Candidate_Profile, the Match_Result's skill analysis, and the Job_Description.
- **Skill_Gap_Report** — The schema-validated structured output of the Skill_Gap_Agent: missing and weak skills relative to the Job_Description, each with a priority.
- **Improvement_Agent** — The LLM_Agent that generates resume rewrites and additions, invoking the Phase 3 resume-coach Prompt_Template through the prompt registry.
- **Improvement_Report** — The schema-validated structured output of the Improvement_Agent.
- **Synthesizer** — The Deterministic_Agent (non-LLM terminal node) that combines all upstream agent outputs into the final Analysis_Result, including degraded outputs from failed nodes.
- **Analysis_Result** — The final combined output of a completed Agent_Job: the synthesized response plus per-agent trace summaries, persisted and returned to the Web_App.
- **Agent_Job** — A row in the `agent_jobs` table representing one requested Agent_Graph execution: id (UUIDv7), user_id, match_id, status, created_at, started_at, completed_at, error details. Owned by a User_Account.
- **Job_Status** — The lifecycle state of an Agent_Job: exactly one of `queued`, `running`, `completed`, `failed`.
- **Agent_Run** — A row in the `agent_runs` table recording one Agent invocation within an Agent_Job: id (UUIDv7), job_id, agent_name, input state, output state, latency_ms, status.
- **Job_Queue** — The SQS queue (LocalStack locally, AWS SQS deployed) through which the API_App hands Agent_Jobs to the Agent_Worker.
- **Agent_Worker** — The dedicated worker process at `apps/api/src/matchlayer_api/workers/agent_worker.py` (own Dockerfile at `infra/docker/worker.Dockerfile`) that consumes the Job_Queue and executes the Agent_Graph.
- **Agent_Cache** — The cache of completed Agent outputs keyed by agent name and input hash, scoped to a single User_Account, never shared across users, per `security.md`.
- **Degraded_Output** — The schema-conformant non-LLM fallback output an Agent contributes to Agent_State when its execution fails, marked as degraded, allowing the graph to complete.
- **Trace_Span** — An OpenTelemetry span emitted for one Agent invocation (and for the enclosing job), carrying identifiers and metrics but never Restricted PII.
- **Progress_UI** — The Web_App polling-based interface showing per-step Agent_Job progress and, behind a "Show reasoning" toggle, per-agent outputs.
- **Rate_Limiter** — The Redis-backed rate limiting infrastructure from `phase-1-auth`, applied to the new endpoints.

## Requirements

### Requirement 1: LangGraph Orchestration with Typed State

**User Story:** As a developer, I want the AI pipeline expressed as a LangGraph graph over a typed state schema, so that multi-step reasoning is composable, inspectable, and extensible without rewiring feature code.

#### Acceptance Criteria

1. THE Agent_Graph SHALL be defined with LangGraph in `apps/api/src/matchlayer_api/ml/agents/graph.py`, with each of the five Agents (Resume_Analysis_Agent, ATS_Agent, Skill_Gap_Agent, Improvement_Agent, Synthesizer) as a distinct node and edges encoding execution order, and no Agent logic SHALL execute outside the Agent_Graph in the production analyze path.
2. THE Agent_State SHALL be a typed Pydantic model defined in `apps/api/src/matchlayer_api/ml/agents/state.py`, every node SHALL receive Agent_State and return Agent_State or a typed Pydantic partial update of it, and no untyped dict SHALL pass between nodes, with the `ml/agents/` package passing `mypy --strict` per `conventions.md`.
3. THE Agent_State SHALL carry the Resume and Job_Description by identifier plus the redacted or derived content downstream nodes consume (PII_Redactor-transformed text, the Candidate_Profile, per-Agent outputs, and per-Agent status flags), and the serialized Agent_State at every node boundary SHALL contain no raw unredacted Resume `extracted_text`, so that persisted state snapshots contain no raw Restricted PII.
4. Each Agent SHALL have exactly one responsibility as defined in the Glossary, and no Agent SHALL perform the responsibility assigned to another Agent (for example, the ATS_Agent SHALL NOT generate improvement text and the Improvement_Agent SHALL NOT compute scores).
5. THE Agent_Graph SHALL execute the Skill_Gap_Agent and the Improvement_Agent as parallel branches that each depend on the Resume_Analysis_Agent's output, THE ATS_Agent SHALL depend on no other Agent's output (its inputs come from the persisted Match_Result per Requirement 4), and THE Synthesizer SHALL execute only after the Resume_Analysis_Agent, ATS_Agent, Skill_Gap_Agent, and Improvement_Agent have all completed (normally or with a Degraded_Output), so independent work does not serialize.
6. THE Resume_Analysis_Agent and the Improvement_Agent SHALL be the only nodes that invoke the LLM_Client, and THE ATS_Agent, Skill_Gap_Agent, and Synthesizer SHALL make no LLM_Provider call under any input.
7. WHEN the Agent_Graph is invoked with a valid Agent_State for a Match_Result — one that passes Pydantic validation and references an existing Match_Result — THE Agent_Graph SHALL produce a final Agent_State containing a schema-validated Analysis_Result, including when one or more non-Synthesizer nodes contributed only a Degraded_Output per Requirement 8.
8. IF the Agent_Graph is invoked with an Agent_State that fails Pydantic validation or references a Match_Result that does not exist, THEN THE Agent_Graph SHALL fail before any Agent node executes, and THE Agent_Worker SHALL transition the enclosing Agent_Job to `failed` with a structured error containing no Restricted PII per Requirement 12.

### Requirement 2: Graph State Persistence via Postgres Checkpointer

**User Story:** As a developer, I want graph state checkpointed in Postgres, so that in-flight and past executions are inspectable and the system does not depend on worker memory.

#### Acceptance Criteria

1. THE Agent_Graph SHALL be compiled with LangGraph's Postgres-backed Checkpointer in the Agent_Worker's production analyze path, using the existing application PostgreSQL instance, with connection settings read via `pydantic-settings` configuration and never from hard-coded values or direct environment reads.
2. WHEN an Agent_Graph execution transitions between nodes, THE Checkpointer SHALL persist the Agent_State snapshot for that transition, keyed to the owning Agent_Job's UUIDv7 identifier as the LangGraph thread identifier, so every checkpoint row is attributable to exactly one Agent_Job.
3. THE Checkpointer SHALL persist no Agent_State snapshot containing raw unredacted Resume `extracted_text`, per Requirement 1 criterion 3, so Checkpointer rows inherit the Internal classification of agent traces rather than Restricted.
4. IF the Checkpointer is unavailable or a checkpoint write fails during an execution, THEN THE Agent_Worker SHALL continue the in-memory execution of the current Agent_Graph run to completion, THE terminal Job_Status SHALL be determined solely by graph execution (a checkpoint failure alone SHALL never yield `failed`), and each failed checkpoint write SHALL produce one structured warning log containing the Agent_Job id and the failure reason and no Restricted PII, so checkpoint persistence is best-effort and never fails a run.
5. THE database objects required by the Checkpointer SHALL be created by invoking LangGraph's setup routine from within an Alembic migration, and neither the API_App nor the Agent_Worker SHALL create or alter Checkpointer schema at runtime, so schema management stays in one place per `conventions.md`.
6. WHEN the Checkpointer is queried by an Agent_Job's identifier, it SHALL return the persisted Agent_State snapshots for that job's execution, for in-flight and completed runs alike, so past executions are inspectable.

### Requirement 3: Resume Analysis Agent

**User Story:** As a job seeker, I want the system to build a structured profile of my resume, so that downstream analysis works from an organized understanding rather than raw text.

#### Acceptance Criteria

1. WHEN an Agent_Job executes, THE Resume_Analysis_Agent SHALL produce a Candidate_Profile from the Resume's `extracted_text` via the LLM_Client, with the text transformed by the PII_Redactor before transmission per Requirement 9, making at most one LLM_Client call per execution and zero calls on an Agent_Cache hit per Requirement 9 criterion 7.
2. THE Candidate_Profile SHALL be a schema-validated Pydantic object containing at minimum: the resume's detected sections, a list of extracted skills, a list of experience entries (role, organization, duration — each sub-field MAY be null where not detectable), and a list of detected gaps or weaknesses; each list MAY be empty, and an output failing schema validation SHALL route to the degraded path of criterion 4.
3. THE Resume_Analysis_Agent's prompt SHALL be a versioned Prompt_Template (`agent_resume_analysis.v1` or later) resolved through the Phase 3 prompt registry, with structured message roles, and the redacted resume text SHALL sit entirely within the delimited user-content region per the Phase 3 prompt-injection defenses.
4. IF the LLM call fails, the output fails schema validation, or the node exceeds the per-node timeout of Requirement 8, THEN THE Resume_Analysis_Agent SHALL contribute a Degraded_Output conforming to the Candidate_Profile schema, built from the Phase 2 Skill_Extractor results and the persisted Match_Result fields, marked as degraded, and the Agent_Graph SHALL continue per Requirement 8.
5. WHEN the Resume_Analysis_Agent completes (normally or degraded), THE Agent_State SHALL carry the Candidate_Profile (or Degraded_Output) forward so the Skill_Gap_Agent and Improvement_Agent consume structured state rather than re-reading raw Resume text.
6. IF the redacted resume text is empty or unavailable when the Resume_Analysis_Agent executes, THEN it SHALL take the degraded path of criterion 4 without making an LLM_Provider call and without consuming a Daily_Quota unit.

### Requirement 4: ATS Agent

**User Story:** As a job seeker, I want the deterministic ATS score included in the agent analysis with a confidence tag, so that the numeric assessment stays consistent with the rest of the product.

#### Acceptance Criteria

1. WHEN an Agent_Job executes and the persisted Match_Result does not contain a score produced by the currently active Scorer_Version, THE ATS_Agent SHALL obtain the composite score for the Match_Result's resume + job-description pair by invoking the Phase 2 `Semantic_Match_Scorer` (including its Degraded_Mode ladder), and SHALL NOT reimplement, modify, or bypass the Phase 2 scoring logic.
2. THE ATS_Agent SHALL tag its score output with a Confidence_Level of exactly `high`, `medium`, or `low`, derived by a deterministic rule documented in the repository whose inputs are limited to observable values — at minimum: (a) whether semantic scoring or a Degraded_Mode fallback scorer produced the score, and (b) whether the resume text length and job-description text length fall within the explicit numeric bounds stated in that documented rule — and identical inputs SHALL always yield the identical Confidence_Level.
3. IF the persisted Match_Result already contains a score produced by the currently active Scorer_Version, THEN THE ATS_Agent SHALL reuse the persisted score and breakdown without invoking the `Semantic_Match_Scorer`, and SHALL still derive and attach a Confidence_Level per criterion 2.
4. IF scoring fails entirely — the `Semantic_Match_Scorer` raises an error after exhausting every rung of its Degraded_Mode ladder, or the ATS_Agent exceeds the per-node timeout of Requirement 8 — THEN THE ATS_Agent SHALL contribute a Degraded_Output carrying the persisted Match_Result score fields with Confidence_Level `low`, marked as degraded, and the Agent_Graph SHALL continue per Requirement 8.
5. IF the composite score was produced by a Degraded_Mode fallback scorer rather than semantic scoring, THEN THE ATS_Agent SHALL NOT assign Confidence_Level `high`.
6. WHEN the ATS_Agent completes (normally or degraded), THE ATS_Agent SHALL write to Agent_State an output containing at minimum the composite score, the score breakdown, the Confidence_Level, and the Scorer_Version that produced the score, so the Synthesizer consumes the ATS output from Agent_State per Requirement 7.

### Requirement 5: Skill Gap Agent

**User Story:** As a job seeker, I want a prioritized list of missing and weak skills for the specific job, so that I know what to address first.

#### Acceptance Criteria

1. WHEN an Agent_Job executes, THE Skill_Gap_Agent SHALL produce a Skill_Gap_Report derived deterministically from exactly three inputs — the Candidate_Profile in Agent_State, the Match_Result's persisted matched and missing skills, and the Job_Description's skills as extracted by the Phase 2 Skill_Extractor — making no LLM_Provider call and reading no raw unredacted Resume text, per Requirement 1 criteria 3 and 6.
2. THE Skill_Gap_Report SHALL be a schema-validated Pydantic object in which each identified gap carries: the skill name, a classification of exactly `missing` or `weak`, and an integer priority rank starting at 1 for the highest-priority gap and increasing by 1 per gap with no duplicate ranks; the gap list SHALL be ordered by ascending rank, each skill name SHALL appear at most once, and both the classification rule (as amended: a JD skill present in the Candidate_Profile's skills or the Match_Result's matched skills is covered and produces no gap entry; a skill in neither set is `missing`; `weak` remains a schema-valid classification value but is no longer produced by the classification rule) and the prioritization rule (including its deterministic tie-breaking order) SHALL be documented in the repository.
3. THE Skill_Gap_Agent SHALL be deterministic: two executions with field-for-field identical Agent_State inputs SHALL produce field-for-field identical Skill_Gap_Reports, including identical ordering and ranks, satisfying the re-execution equality bar of Requirement 12 criterion 5.
4. IF the Candidate_Profile in Agent_State is a Degraded_Output, THEN THE Skill_Gap_Agent SHALL still produce a Skill_Gap_Report from the Match_Result's persisted skill analysis alone, marked as derived-from-degraded input via a dedicated field in the Skill_Gap_Report schema, with criteria 2 and 3 continuing to apply to that report.
5. IF the Skill_Gap_Agent raises an error, exceeds the per-node timeout of Requirement 8 criterion 3, or produces output failing schema validation, THEN it SHALL contribute a Degraded_Output conforming to the Skill_Gap_Report schema per Requirement 8 criterion 2, carrying the Match_Result's persisted missing skills each classified `missing` and ranked sequentially from 1 in their persisted order without applying the prioritization rule, marked as degraded, and the Agent_Graph SHALL continue per Requirement 8.
6. WHEN the Skill_Gap_Agent completes (normally, from degraded input, or degraded), THE Skill_Gap_Agent SHALL write its Skill_Gap_Report (or Degraded_Output) to Agent_State, so the Synthesizer consumes the skill-gap output from Agent_State per Requirement 7.
7. IF no gap is identified — every skill extracted from the Job_Description is present in the Candidate_Profile's skills or the Match_Result's persisted matched skills — THEN THE Skill_Gap_Agent SHALL produce a schema-valid Skill_Gap_Report with an empty gap list, and an empty gap list SHALL NOT be treated as a failure or route to the Degraded_Output path of criterion 5.

### Requirement 6: Resume Improvement Agent

**User Story:** As a job seeker, I want concrete rewrites and additions for my resume generated within the agent workflow, so that the analysis ends with actionable output.

#### Acceptance Criteria

1. WHEN an Agent_Job executes, THE Improvement_Agent SHALL produce an Improvement_Report via the LLM_Client, assembling its prompt from the Phase 3 resume-coach Prompt_Template lineage resolved through the prompt registry (never from string literals in agent code, per Requirement 9 criterion 6), making at most one LLM_Client call per execution and zero calls on an Agent_Cache hit per Requirement 9 criterion 7, so Phase 3 prompt content is reused rather than duplicated.
2. THE Improvement_Report SHALL be a schema-validated Pydantic object containing at minimum: a list of improvement actions each carrying an integer priority rank, ordered from highest to lowest priority, and a list of concrete rewrite suggestions each pairing an excerpt of existing resume content (in PII_Redactor-transformed form, never raw unredacted Resume text) with proposed replacement text and a rationale; each list MAY be empty, and an output failing schema validation SHALL route to the degraded path of criterion 4.
3. THE Improvement_Agent's prompt SHALL include the Candidate_Profile from Agent_State and the Match_Result's persisted matched/missing skills, and SHALL NOT depend on the Skill_Gap_Report, since the Improvement_Agent executes in parallel with the Skill_Gap_Agent per Requirement 1 criterion 5; all such content SHALL sit entirely within the delimited user-content region with structured message roles per the Phase 3 prompt-injection defenses.
4. IF the LLM call fails, the output fails schema validation, or the node exceeds the per-node timeout of Requirement 8, THEN THE Improvement_Agent SHALL contribute a Degraded_Output conforming to the Improvement_Report schema, built from the Match_Result's stored rule-based suggestions and missing skills, marked as degraded, and the Agent_Graph SHALL continue per Requirement 8.
5. IF the Candidate_Profile in Agent_State is a Degraded_Output, THEN THE Improvement_Agent SHALL still execute per criterion 1 consuming the degraded Candidate_Profile without branching on output shape per Requirement 8 criterion 2, and the resulting Improvement_Report SHALL be marked as derived-from-degraded input.
6. WHEN the Improvement_Agent completes (normally or degraded), THE Improvement_Agent SHALL write the Improvement_Report (or Degraded_Output) to Agent_State so the Synthesizer consumes it per Requirement 7.

### Requirement 7: Synthesizer

**User Story:** As a job seeker, I want one coherent final result from the multi-agent run, so that I don't have to assemble the pieces myself.

#### Acceptance Criteria

1. WHEN all four upstream Agents (Resume_Analysis_Agent, ATS_Agent, Skill_Gap_Agent, Improvement_Agent) have completed (normally or with Degraded_Output), THE Synthesizer SHALL combine the Candidate_Profile, the ATS_Agent output (composite score, score breakdown, Confidence_Level, and Scorer_Version per Requirement 4 criterion 6), the Skill_Gap_Report, and the Improvement_Report into a single Analysis_Result that passes its Pydantic schema validation, without any LLM_Provider call and using only content already present in Agent_State, so the Analysis_Result contains no raw unredacted Resume `extracted_text` per Requirement 1 criterion 3.
2. THE Analysis_Result SHALL identify, for each of the four contributing Agents, whether that Agent's output was normal or degraded, derived from the per-Agent status flags carried in Agent_State, so the Web_App can visibly mark degraded sections per Requirement 15 criterion 2.
3. THE Synthesizer SHALL be a deterministic function of its Agent_State inputs: given field-for-field identical upstream Agent outputs, status flags, and trace metadata, THE Synthesizer SHALL produce a field-for-field identical Analysis_Result across repeated invocations, with no dependence on wall-clock time, randomness, or external I/O.
4. THE Analysis_Result SHALL contain at minimum: (a) the composite score, score breakdown, Confidence_Level, and Scorer_Version from the ATS_Agent output; (b) every Skill_Gap_Report entry with its skill name, `missing`/`weak` classification, and priority rank; (c) every Improvement_Report entry, including the prioritized improvement actions and each rewrite suggestion with its rationale; (d) the Candidate_Profile; and (e) a per-agent trace summary per criterion 5 — so the agent workflow response is a superset of the score context, gap analysis, and improvement guidance the Phase 3 features returned for the same Match_Result.
5. THE Analysis_Result SHALL include one trace summary per contributing Agent, each containing at minimum: the agent name, the completion status (normal or degraded), the invocation latency in milliseconds from the corresponding Agent_Run row, and — when the Agent degraded — the structured failure reason recorded per Requirement 8 criterion 4, containing no Restricted PII.
6. IF the Synthesizer raises an error, exceeds the per-node timeout of Requirement 8 criterion 3, or produces output that fails Analysis_Result schema validation, THEN THE Agent_Worker SHALL transition the Agent_Job to `failed` with a structured error containing no Restricted PII, recorded per Requirement 12, and no partial Analysis_Result SHALL be persisted or returned to the Web_App; this is the only single-node failure permitted to fail the job, since no final result can exist without synthesis.

### Requirement 8: Per-Node Graceful Degradation

**User Story:** As an operator, I want one failing agent to degrade its own output only, so that users still get a useful result when a single step breaks.

#### Acceptance Criteria

1. IF any non-Synthesizer Agent raises an error, exceeds the per-node timeout of criterion 3, or produces output failing Pydantic schema validation, THEN that Agent SHALL contribute its Degraded_Output (as defined for that Agent in Requirements 3–6) to Agent_State, and THE Agent_Graph SHALL continue executing every remaining node — including when multiple non-Synthesizer Agents degrade within the same run, each degrading independently without affecting the execution of any other node.
2. Each Agent's Degraded_Output SHALL pass validation against the exact same Pydantic schema as that Agent's normal output, with degradation indicated only by that Agent's per-Agent status flag in Agent_State (per Requirement 1 criterion 3) and a dedicated degraded-marker field on the output, so downstream nodes consume normal and degraded outputs through an identical schema and never branch on output shape.
3. THE Agent_Worker SHALL enforce a per-node wall-clock timeout on every Agent invocation, measured from node invocation start to output return, configured by `MATCHLAYER_AGENT_NODE_TIMEOUT_SECONDS` read via `pydantic-settings` (default 20, per Requirement 16 criterion 2); and WHEN a node exceeds this timeout, THE Agent_Worker SHALL abandon that node's in-flight work, discard any result the node produces after the timeout, and route the node to its Degraded_Output path per criterion 1.
4. WHEN an Agent takes its Degraded_Output path, THE Agent_Worker SHALL record the corresponding Agent_Run row with status `degraded` and a structured failure reason that identifies which trigger applied (error, timeout, or schema-validation failure) and contains no Restricted PII per `security.md`; and WHEN the Synthesizer subsequently succeeds, THE Agent_Job SHALL reach Job_Status `completed`.
5. IF every LLM_Agent degrades in a single run (for example, Spend_Circuit_Breaker open or LLM_Provider outage), THEN THE Agent_Graph SHALL complete with a schema-validated Analysis_Result assembled entirely from Deterministic_Agent outputs and Degraded_Outputs, THE Agent_Job SHALL reach Job_Status `completed`, and `GET /api/v1/jobs/{id}` for that job SHALL return HTTP 200 with that Analysis_Result, never a 5xx status.
6. IF constructing an Agent's Degraded_Output itself raises an error (for example, expected persisted Match_Result fields are unavailable), THEN that Agent SHALL contribute a minimal schema-valid Degraded_Output with empty or null optional content, marked as degraded, and the construction failure SHALL be recorded in the Agent_Run failure reason per criterion 4, so no non-Synthesizer node failure can transition the Agent_Job to `failed` (consistent with Requirement 7 criterion 5).

### Requirement 9: Reuse of Phase 3 LLM Plumbing and Cost Controls

**User Story:** As an operator, I want agent LLM calls governed by the exact same client, redaction, quota, spend, logging, and prompt-versioning machinery as Phase 3, so that cost and privacy guarantees hold across the whole system.

#### Acceptance Criteria

1. Every LLM_Provider call made by any Agent SHALL flow through the Phase 3 LLM_Client, and no Agent, graph, or worker module SHALL construct an HTTP request to the LLM_Provider directly or instantiate a second provider client.
2. Every text sent to the LLM_Provider by an Agent SHALL be transformed by the Phase 3 PII_Redactor before transmission, under the same redaction rules and the documented Redaction_Exception of `docs/redaction-policy.md` as Phase 3, with no Phase 4-specific redaction rule drift.
3. Every agent LLM call SHALL produce an LLM_Invocation_Log entry (prompt version, model, input hash over redacted text, output, latency, token usage, cost) and SHALL count toward the Spend_Circuit_Breaker's monthly spend accounting.
4. WHEN the API_App receives an analyze request, it SHALL verify the requesting User_Account has at least 2 Daily_Quota units remaining; IF fewer than 2 units remain, THEN THE API_App SHALL reject with a 429 RFC 7807 response including the UTC reset time, creating no Agent_Job row and enqueuing no message; and each LLM_Agent SHALL consume exactly one Daily_Quota unit via the Phase 3 atomic reserve at call initiation — paths that make no LLM_Provider call (Agent_Cache hit, Degraded_Output without a call, breaker open, empty input) SHALL consume zero units.
5. WHILE the Spend_Circuit_Breaker is open, THE LLM_Agents SHALL take their Degraded_Output paths without any LLM_Provider call and without consuming Daily_Quota units, THE Deterministic_Agents SHALL run normally, and new analyze requests SHALL still be accepted and complete with degraded LLM outputs per Requirement 8 criterion 5.
6. Every agent prompt SHALL be a versioned Prompt_Template resolved through the Phase 3 active-version registry, with new agent prompts added as new versioned files (`agent_resume_analysis.v1`, plus the reused coach lineage for the Improvement_Agent), never as string literals in agent code.
7. THE Agent_Cache SHALL store completed non-degraded per-agent outputs keyed by agent name, prompt version (for LLM_Agents), and input hash computed over redacted input, scoped to the owning User_Account and never shared across users; Degraded_Outputs SHALL never be cached; and WHEN an Agent's cache key matches a stored entry, THE Agent SHALL return the cached output without an LLM_Provider call and without consuming Daily_Quota for that node, with the Agent_Run row still recorded per Requirement 12 criterion 2.
8. THE repository's `docs/costs.md` SHALL be updated with the Phase 4 cost posture: agent runs make up to 2 LLM calls (bounded by Daily_Quota and the Spend_Circuit_Breaker), and SQS usage at expected volume fits the AWS free tier (1M requests/month), keeping total Phases 1–5 spend under the $20/month ceiling of `product.md`.
9. IF an LLM_Agent's atomic Daily_Quota reserve fails at call time (the quota was exhausted between job acceptance and call initiation), THEN that LLM_Agent SHALL take its Degraded_Output path without an LLM_Provider call, with the quota-exhausted failure reason recorded per Requirement 8 criterion 4.
10. IF an Agent_Cache read or write fails, THEN THE Agent SHALL proceed as if on a cache miss (read failure) or return its computed output normally (write failure), emitting one structured warning log containing no Restricted PII, so cache availability never fails a node or a job.

### Requirement 10: Async Analyze and Job Polling API

**User Story:** As a job seeker, I want to trigger an analysis and poll its progress, so that a long-running multi-agent workflow doesn't hold my request open.

#### Acceptance Criteria

1. WHEN a User_Account sends `POST /api/v1/matches/{id}/analyze` for a Match_Result it owns, THE API_App SHALL create an Agent_Job with a UUIDv7 identifier and Job_Status `queued`, enqueue it on the Job_Queue per Requirement 11 criterion 1, and respond `202 Accepted` with a body carrying the job id (UUIDv7 exposed as a string), the Job_Status `queued`, and a pollable job URL referencing `GET /api/v1/jobs/{id}` — without executing any Agent synchronously in the request path; enqueue failure follows Requirement 11 criterion 6.
2. WHEN a User_Account sends `GET /api/v1/jobs/{id}` for an Agent_Job it owns, THE API_App SHALL return the Job_Status (exactly one of `queued`, `running`, `completed`, `failed`), per-agent step statuses derived from Agent_Run rows (`pending` for an Agent with no Agent_Run row yet, else that row's status including `degraded`), and ISO 8601 UTC timestamps with `Z` suffix per `conventions.md` (`created_at` always present; `started_at` and `completed_at` present when set, null otherwise).
3. WHEN the polled Agent_Job's Job_Status is `completed`, THE response SHALL include the Analysis_Result; and WHEN it is `failed`, THE response SHALL include the structured error details recorded per Requirement 12, containing no Restricted PII and safe to display.
4. IF a User_Account requests analysis or job status for a resource it does not own or that does not exist, THEN THE API_App SHALL respond with a 404 RFC 7807 response whose body shape is identical in the not-owned and not-found cases (excepting `request_id`), without revealing whether the resource exists, per `security.md` ownership indistinguishability.
5. IF an Agent_Job with Job_Status `queued` or `running` already exists for the same Match_Result and User_Account, THEN a subsequent `POST /api/v1/matches/{id}/analyze` SHALL return `202 Accepted` with that existing job's id rather than enqueuing a duplicate — at most one non-terminal Agent_Job SHALL exist per (Match_Result, User_Account) pair even under concurrent requests; and WHEN the prior job has reached a terminal Job_Status, a new analyze request SHALL create a fresh Agent_Job.
6. THE API_App SHALL validate all request input with Pydantic, set `X-Robots-Tag: noindex, nofollow` on all responses from both endpoints, and return all errors in the RFC 7807 envelope, per `security.md` and `conventions.md`.
7. THE Rate_Limiter SHALL bound both endpoints per User_Account with limits configurable via `pydantic-settings` (defaults: 10 analyze requests per minute, 120 job polls per minute), and a request exceeding its limit SHALL receive a 429 RFC 7807 response.
8. THE new endpoints SHALL appear in the FastAPI OpenAPI schema and be covered by the existing OpenAPI→TS/Zod codegen so `packages/shared-types/` exposes their request/response types, with the CI drift check applying.

### Requirement 11: SQS Queue and Worker Process

**User Story:** As a developer, I want agent execution moved to a queue-fed worker, so that the API stays responsive and the async architecture matches where the product is heading.

#### Acceptance Criteria

1. WHEN the API_App accepts an analyze request, it SHALL persist the Agent_Job row with Job_Status `queued` before enqueuing, then enqueue a message on the Job_Queue (SQS) whose body carries identifiers only (job id, match id, user id) plus the trace-context headers of Requirement 13 criterion 4 — never Resume text or Job_Description text — with queue URL, region, and credentials read via `pydantic-settings` configuration.
2. THE Agent_Worker SHALL run as a separate process from the API_App (module `apps/api/src/matchlayer_api/workers/agent_worker.py`, image built from `infra/docker/worker.Dockerfile`), consuming the Job_Queue, loading job context from the database by identifier, and executing the Agent_Graph.
3. THE local development environment SHALL emulate SQS via LocalStack in `docker-compose.yml` so the full async path (enqueue → consume → execute) runs locally without AWS credentials, and THE deployed environment SHALL use real AWS SQS, with the two environments differing only in configuration values.
4. WHEN the Agent_Worker receives a message referencing an Agent_Job in Job_Status `queued`, it SHALL transition the job to `running` (recording `started_at` as an ISO 8601 UTC timestamp), execute the Agent_Graph, then transition to `completed` (recording `completed_at`) or `failed` (recording structured error details containing no Restricted PII per Requirement 12), and delete the message only after the terminal transition is persisted.
5. IF the Agent_Worker crashes or the message visibility timeout elapses before deletion, THEN SQS redelivery SHALL be handled safely using a persisted per-job attempt counter: (a) a redelivered message referencing an Agent_Job already in a terminal state SHALL be acknowledged without re-execution; (b) a redelivered message referencing a job in `running` with fewer than `MATCHLAYER_AGENT_MAX_ATTEMPTS` (default 2, read via `pydantic-settings`) recorded attempts SHALL be re-executed; and (c) a redelivered message for a job whose attempt counter has reached `MATCHLAYER_AGENT_MAX_ATTEMPTS` SHALL transition the job to `failed` and be acknowledged.
6. IF the Job_Queue is unreachable when the API_App attempts to enqueue, THEN THE API_App SHALL respond with a 503 RFC 7807 response whose detail is safe to display, and the Agent_Job row SHALL NOT remain in `queued` (not persisted, rolled back, or transitioned to `failed`), so no orphaned row exists that no worker will ever pick up.
7. IF the Agent_Worker receives a malformed message or a message referencing an Agent_Job that does not exist, THEN it SHALL log a structured warning containing no Restricted PII and acknowledge (delete) the message, so a poison message can never crash-loop the Agent_Worker.
8. THE API_App's analyze request path SHALL NOT read Resume `extracted_text` or Job_Description text; all resume-content processing within the analyze path SHALL occur in the Agent_Worker under the per-node wall-clock bounds of Requirement 8 criterion 3, satisfying the `security.md` Phase 4 sandboxed-parsing direction.

### Requirement 12: Job and Run Persistence

**User Story:** As a developer, I want every job and every agent invocation persisted, so that debugging and replay never depend on ephemeral logs.

#### Acceptance Criteria

1. THE database SHALL gain an `agent_jobs` table (UUIDv7 `id`; `user_id` as a foreign key to the users table; `match_id` as a foreign key to the match_results table; `status` holding exactly one Job_Status value — `queued`, `running`, `completed`, or `failed`; `created_at`, plus nullable `started_at` and `completed_at`, all stored as UTC timestamps; and a structured error field that SHALL be null unless Job_Status is `failed`) and an `agent_runs` table (UUIDv7 `id`; `job_id` as a foreign key to `agent_jobs`; `agent_name`; input state; output state; `latency_ms`; `status` holding exactly one of `completed`, `degraded`, or `failed`; and a structured failure-reason field that SHALL be null when status is `completed`), created by Alembic migrations with indexes covering at minimum `agent_runs.job_id`, `agent_jobs.user_id`, and the `agent_jobs` (`match_id`, `user_id`, `status`) lookup used by the in-flight idempotency check of Requirement 10, with each index's rationale documented in its migration per `conventions.md`.
2. WHEN an Agent completes (normally, degraded, or via an Agent_Cache hit per Requirement 9 criterion 7), THE Agent_Worker SHALL persist exactly one Agent_Run row for that Agent invocation capturing its input state, its output state, its latency in milliseconds measured from node invocation start to output return (the same boundary as the per-node timeout of Requirement 8 criterion 3), and its status — `completed` for normal completion, or `degraded` together with the structured failure reason of Requirement 8 criterion 4 identifying which trigger applied (error, timeout, or schema-validation failure).
3. Persisted Agent_Run input and output state SHALL contain only redacted or derived content per Requirement 1 criterion 3 — never raw unredacted Resume text — so `agent_runs` rows carry the Internal classification while honoring the Restricted classification of the underlying resume content.
4. THE API_App SHALL expose Agent_Job and Agent_Run data (including trace summaries) only to the owning User_Account; IF a request targets an Agent_Job or Agent_Run that does not exist or is owned by another User_Account, THEN THE API_App SHALL respond with a 404 RFC 7807 response without revealing whether the resource exists, per Requirement 10 criterion 3.
5. THE persisted data for a completed Agent_Job — its Agent_Run rows plus the recorded prompt versions, PII_Redactor version, model identifier, and input hashes from the associated LLM_Invocation_Log entries — SHALL be sufficient to reproduce the run from inputs alone, verified as follows: for each Deterministic_Agent, re-executing the Agent against the persisted input state SHALL produce output field-for-field identical to the persisted output state (per the determinism guarantees of Requirements 4, 5, and 7); for each LLM_Agent, the transmitted prompt SHALL be exactly reconstructable from the persisted input state, the recorded prompt version, and the recorded PII_Redactor version, with reconstruction confirmed by the recomputed input hash equaling the input hash recorded in the corresponding LLM_Invocation_Log entry; and the repository SHALL include an automated test demonstrating both checks for at least one completed Agent_Job.
6. Agent_Job and Agent_Run rows SHALL be retained for Phase 5 evaluation consumption: no Phase 4 code path SHALL delete them on job completion or on any schedule, Agent_Run rows SHALL be immutable once written, and the only permitted mutations of an Agent_Job row after creation SHALL be its Job_Status lifecycle transitions and the associated timestamp and error fields per Requirement 11 criterion 4.
7. IF the Synthesizer fails per Requirement 7 criterion 6 and the Agent_Job transitions to `failed`, THEN THE Agent_Worker SHALL persist the Synthesizer's Agent_Run row with status `failed` and a structured failure reason containing no Restricted PII before recording the terminal Job_Status, and the Agent_Run rows already persisted for upstream Agents SHALL be retained, so failed jobs remain debuggable from persisted data alone.

### Requirement 13: OpenTelemetry Tracing

**User Story:** As an operator, I want every agent invocation traced as a span, so that I can see where time goes and what failed in any run.

#### Acceptance Criteria

1. WHEN the Agent_Worker executes an Agent_Job, THE Agent_Worker SHALL emit one Trace_Span for that Agent_Job execution and one child Trace_Span per Agent invocation (including invocations resolved by an Agent_Cache hit per Requirement 9 criterion 7), with the job span carrying the Agent_Job id as an attribute, and each child span carrying the agent name, the invocation status (exactly one of `completed`, `degraded`, or `failed`, equal to the status of the corresponding Agent_Run row per Requirement 12 criterion 2), and the invocation duration in milliseconds measured over the same boundary as the per-node timeout of Requirement 8 criterion 3 (node invocation start to output return).
2. WHEN an LLM_Agent invocation makes an LLM_Client call, THE Agent_Worker SHALL record on that invocation's child Trace_Span the prompt version, model identifier, and input hash (computed over redacted text) as span attributes, each equal to the corresponding value recorded in that call's LLM_Invocation_Log entry so span data and invocation logs cross-reference exactly; and WHEN an LLM_Agent invocation makes no LLM_Client call (Agent_Cache hit, or a Degraded_Output path without a call per Requirement 9), THE Agent_Worker SHALL still emit the child span per criterion 1 with these three attributes permitted to be absent.
3. THE API_App and THE Agent_Worker SHALL emit no Trace_Span whose name, attributes, or events contain Restricted PII: no Resume text, Job_Description text, prompt content, or LLM output text SHALL appear in any span name, span attribute, or span event, per `security.md`; Restricted content SHALL be referenced in spans by identifier or hash only.
4. WHEN the API_App enqueues a Job_Queue message per Requirement 11 criterion 1, THE API_App SHALL include the current trace context in that message as identifiers/headers only (never Resume text or Job_Description text), and WHEN the Agent_Worker processes a message carrying valid trace context, THE Agent_Worker SHALL continue that trace so the spans of criterion 1 carry the originating request's trace identifier, covering request acceptance through job completion in a single end-to-end trace.
5. THE OpenTelemetry exporter and its endpoint SHALL be configurable via `pydantic-settings` (listed in `.env.example` per Requirement 16), and IF no exporter is configured, THEN tracing SHALL operate as a no-op: every analyze request and Agent_Job SHALL produce a response status, Job_Status, and Analysis_Result identical to what an exporter-configured run would produce, and no request or job SHALL fail or degrade due to the absence of an exporter.
6. IF the Agent_Worker consumes a Job_Queue message whose trace context is missing or invalid (for example, a redelivered or malformed message), THEN THE Agent_Worker SHALL start a new trace for that Agent_Job execution, emit the spans of criterion 1 under it, and process the message normally, so absent trace context never fails or skips message processing.
7. IF a configured exporter is unreachable or a span export fails at runtime, THEN the export failure SHALL NOT alter any request outcome, Job_Status, or Analysis_Result, and THE affected process (API_App or Agent_Worker) SHALL record the export failure via at most one structured warning log per failure containing no Restricted PII, so tracing remains best-effort end to end.

### Requirement 14: Performance and Latency Budget

**User Story:** As a job seeker, I want the full analysis to finish quickly, so that waiting on the progress screen feels acceptable.

#### Acceptance Criteria

1. WHEN an Agent_Job executes with typical inputs (a resume and job description within the Phase 1 upload limits), with no Agent_Cache hits, and under normal LLM_Provider latency — defined as every LLM_Provider call made during the run completing within 10 seconds — THE elapsed time from the Agent_Job's recorded `started_at` timestamp (the Job_Status `running` transition per Requirement 11 criterion 4) to its recorded `completed_at` timestamp (the Job_Status `completed` transition) SHALL be less than 30 seconds.
2. THE Agent_Graph SHALL execute the Skill_Gap_Agent and Improvement_Agent parallel branches of Requirement 1 criterion 5 concurrently, such that the elapsed wall-clock time from the Resume_Analysis_Agent's output return to the Synthesizer's invocation start is less than the sum of the two branch Agents' individual execution durations as recorded in their Agent_Run `latency_ms` values (Requirement 12 criterion 2), and the repository SHALL include an automated test demonstrating this overlap by injecting a fixed delay into each branch node and asserting the combined branch phase completes in less than the sum of the two injected delays.
3. Every Agent LLM_Provider call SHALL be bounded by both the per-node timeout of Requirement 8 criterion 3 (`MATCHLAYER_AGENT_NODE_TIMEOUT_SECONDS`, default 20) and the Phase 3 LLM_Client per-request timeout (`MATCHLAYER_LLM_TIMEOUT_SECONDS`, default 60), whichever elapses first, and THE repository README runbook SHALL document the worst-case Agent_Job duration as a formula over those two settings, the number of Agents on the Agent_Graph's longest sequential path, and `MATCHLAYER_AGENT_MAX_ATTEMPTS` (Requirement 11 criterion 5), together with the computed numeric worst-case value in seconds at the default configuration.
4. THE repository SHALL include an automated test, runnable in CI, that executes the full Agent_Graph for one Agent_Job using a mocked LLM_Client whose injected per-call latency equals the 10-second normal-latency bound of criterion 1 and asserts the criterion 1 elapsed time (`started_at` to `completed_at`) is less than 30 seconds; and THE README runbook SHALL document a step-by-step procedure for repeating that measurement against the real LLM_Provider, reading the measured duration from the persisted `started_at` and `completed_at` timestamps.

### Requirement 15: Frontend Progress and Reasoning UI

**User Story:** As a job seeker, I want to watch the analysis progress step by step and optionally inspect each agent's output, so that the system feels transparent rather than a black box.

#### Acceptance Criteria

1. WHEN a User_Account triggers an analysis from the Match_Result page, THE Web_App SHALL call the analyze endpoint (`POST /api/v1/matches/{id}/analyze`), then poll `GET /api/v1/jobs/{id}` at a fixed interval of no less than 1 second and no more than 5 seconds (remaining within the 120-polls-per-minute Rate_Limiter default of Requirement 10 criterion 7), rendering a Progress_UI with exactly one labeled step per Agent — five steps total (for example "Analyzing resume…", "ATS scoring…", "Finding skill gaps…", "Generating improvements…", "Combining results…") — where each step's displayed status is derived solely from the polled per-agent step statuses (`pending`, `completed`, `degraded` per Requirement 10 criterion 2), is updated within one polling interval of the poll response that changed it, and status changes are announced via an `aria-live="polite"` region per the `design.md` accessibility baseline.
2. WHEN a polled response reports Job_Status `completed`, THE Web_App SHALL render the Analysis_Result, and every rendered section whose contributing Agent produced a Degraded_Output (as indicated by that Agent's degraded-marker field per Requirement 8 criterion 2, or its `degraded` step status) SHALL display a visible degraded indicator that distinguishes it from sections produced from normal outputs.
3. THE Progress_UI SHALL include a "Show reasoning" toggle that defaults to off (reasoning hidden) on every page load; WHEN the toggle is enabled, THE Web_App SHALL reveal the per-agent outputs from the completed job's trace summaries in the Analysis_Result, rendered as plain text or as markdown through a safe renderer with embedded HTML stripped, and SHALL never render this content via `dangerouslySetInnerHTML`, per `security.md`.
4. IF a polled response reports Job_Status `failed`, or polling receives a 404, 429, or 5xx response, THEN THE Web_App SHALL stop polling before the next scheduled poll and SHALL render an error state specific to the observed case — for `failed`, displaying the structured error details from the job response (safe to display per Requirement 10 criterion 3); for 404, indicating the job is not available; for 429, indicating the rate or quota limit including any reset time present in the response; for 5xx, indicating a temporary failure — each error state offering at least one recovery action (retrying the poll or starting a new analysis); and polling SHALL always stop within one polling interval of observing any terminal Job_Status (`completed` or `failed`).
5. THE Web_App SHALL use the generated types and Zod schemas from `packages/shared-types/` for the analyze and job endpoints, parsing every polled response at runtime with the generated Zod schema per `conventions.md`; and IF a polled response fails Zod parsing, THEN THE Web_App SHALL stop polling and render the temporary-failure error state of criterion 4.
6. WHERE streaming of step results as they complete is implemented, it SHALL be additive to (not a replacement for) the polling path; streaming is a nice-to-have and its absence SHALL NOT block Phase 4 completion.
7. IF no terminal Job_Status is observed within 120 seconds of the first poll (a bound exceeding the 30-second typical-path budget of Requirement 14), THEN THE Web_App SHALL stop polling and render a timeout error state offering a recovery action to resume polling or start a new analysis.

### Requirement 16: Health Reporting, Configuration, and Documentation

**User Story:** As an operator, I want the agent subsystem observable in health checks and fully documented, so that running and debugging Phase 4 doesn't require reading source code.

#### Acceptance Criteria

1. WHEN the `/healthz` endpoint is invoked, THE API_App SHALL include an `agents` field in the response body whose value is exactly `available` or `unavailable`, following the Phase 2 `semantic_scoring` and Phase 3 `llm` field pattern, where `available` means the Job_Queue is reachable from the API_App at the time of evaluation and `unavailable` means it is not.
2. THE API*App SHALL read every configuration setting introduced by Phase 4 (Job_Queue settings, per-node timeout in seconds, maximum delivery attempts, OpenTelemetry exporter settings, and agent-specific bounds) exclusively through the existing `pydantic-settings` `Settings` object using the `MATCHLAYER*` environment-variable prefix, with no direct environment reads in business logic.
3. THE repository SHALL contain `docs/adr/0008-agent-architecture.md` containing the Status, Date, Context, Decision, Rationale, Consequences, and Alternatives sections defined by the `adrs.md` template, and describing the Agent_Graph nodes, edges, parallel branches, the Agent_State schema, Checkpointer usage, and the per-node degradation policy.
4. THE repository README, or a runbook in `docs/runbooks/` linked from the README, SHALL document the full local async path with at least one executable command per step: starting LocalStack via docker-compose, starting the Agent_Worker, triggering an analysis via `POST /api/v1/matches/{id}/analyze`, polling job status via `GET /api/v1/jobs/{id}`, and inspecting Agent_Job rows, Agent_Run rows, and OpenTelemetry traces for a completed job.
5. THE API_App SHALL serve every Phase 3 feature endpoint with unchanged request and response contracts after Phase 4 lands, verified by the pre-existing Phase 3 test suite passing without modification to its test assertions.
6. IF the `agents` subsystem is `unavailable`, THEN THE `/healthz` endpoint SHALL still return HTTP 200 with `status: "ok"`, and the response SHALL contain no queue URLs, credentials, or endpoint addresses.
7. THE repository SHALL list every Phase 4 configuration setting in `.env.example` with a placeholder value wired to the local docker-compose stack (LocalStack for the Job_Queue) and a comment stating the setting's unit and effect.
8. THE repository SHALL add an ADR 0008 entry to the `adrs.md` index and SHALL NOT create a file named `docs/adr/0004-agent-architecture.md`, superseding the phase doc's reference because ADR 0004 already records the pgvector decision and ADRs are numbered sequentially and immutable.
